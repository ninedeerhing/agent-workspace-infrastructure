# Workflow Gates — AWI 工作流质量门禁

> 本文件定义 AWI 四种工作流中各阶段的质量门禁（Quality Gates）。每个门禁定义进入条件、退出条件和验证要求。
>
> 与 `workflow-state.json` 配合使用：`workflow-state.json` 记录当前工作流状态和门禁通过状态，本文件定义每个门禁的具体标准。

---

## 一、门禁系统概述

### 1.1 门禁类型

| 类型 | 符号 | 说明 |
|------|------|------|
| **进入门禁（Entry Gate）** | 🚪 进 | 进入某阶段前必须满足的条件 |
| **退出门禁（Exit Gate）** | 🚪 退 | 退出某阶段时必须满足的条件，也是下一阶段的进入门禁 |
| **检查点（Checkpoint）** | ✓ | 阶段内部的质量检查点，无需阻塞阶段推进 |

### 1.2 门禁通过判定

| 结果 | 含义 | 后续动作 |
|------|------|----------|
| ✅ **PASS** | 所有条件已满足 | 进入下一阶段 |
| ⚠️ **PASS_WITH_WARNING** | 核心条件满足，次要条件有偏差 | 进入下一阶段，记录偏差到 `workflow-state.json` |
| ❌ **FAIL** | 核心条件未满足 | 回退修复，不得进入下一阶段 |
| ⏭️ **SKIPPED** | 该门禁不适用于当前任务 | 记录跳过原因后继续 |

### 1.3 证据链要求

通过的门禁必须附带最小证据集：

1. **门禁名称和编号**：例如 "G-STD-01 INTAKE → RESEARCH"
2. **判定结果**：PASS / PASS_WITH_WARNING / FAIL / SKIPPED
3. **验证方式**：运行了什么命令、阅读了什么文件、执行了什么审查
4. **关键指标**：测试通过数、lint 告警数、typecheck 错误数等
5. **时间戳**：YYYY-MM-DD HH:MM
6. **判定人**：代理角色或人工角色

## 二、标准工作流门禁（Standard Workflow）

> 工作流：`INTAKE → RESEARCH → PLAN → EXECUTE → REVIEW → VERIFY → HANDOFF`

### G-STD-01: INTAKE → RESEARCH

**退出门禁 — 进入 RESEARCH 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-01.1 | 用户目标已明确记录 | **必须** | 检查 `workflow-state.json` 的 `current_context` 中有明确的任务描述 |
| G-STD-01.2 | 任务范围已界定（做什么、不做什么） | **必须** | 任务描述中包含 scope 字段 |
| G-STD-01.3 | 验收标准已定义 | **必须** | 至少 1 条可验证的验收标准 |
| G-STD-01.4 | 风险点已初步识别 | **建议** | 列出已知风险（可为空） |

### G-STD-02: RESEARCH → PLAN

**退出门禁 — 进入 PLAN 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-02.1 | 相关代码文件已定位 | **必须** | 列出需要读取或修改的文件路径 |
| G-STD-02.2 | 外部依赖（SDK/API/框架）用法已确认 | **必须** | 引用官方文档或本地源码证据 |
| G-STD-02.3 | 项目中已有类似模式的实现已理解 | **建议** | 列出参考的已有代码片段位置 |
| G-STD-02.4 | 已知限制和约束已记录 | **建议** | 记录在 research 输出中 |

### G-STD-03: PLAN → EXECUTE

**退出门禁 — 进入 EXECUTE 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-03.1 | 任务已拆分为可执行的子步骤 | **必须** | 至少有 1 个明确可执行的步骤，复杂任务 3+ 个 |
| G-STD-03.2 | 每个步骤有明确的完成定义 | **必须** | 每个步骤有 Done 标准 |
| G-STD-03.3 | 文件变更范围已预估 | **必须** | 列出预计要创建/修改的文件清单 |
| G-STD-03.4 | 测试策略已确定 | **必须** | 说明如何验证（单元测试/集成测试/手动验证） |
| G-STD-03.5 | 依赖关系已排序 | **建议** | 复杂任务需标注步骤间的前置依赖 |

### G-STD-04: EXECUTE → REVIEW

**退出门禁 — 进入 REVIEW 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-04.1 | 所有计划步骤已执行 | **必须** | 对照计划逐项确认 |
| G-STD-04.2 | 代码已保存且无语法错误 | **必须** | 文件可正常解析，IDE 无红色错误提示 |
| G-STD-04.3 | 无遗留的 TODO/FIXME | **建议** | 搜索 TODO\|FIXME\|HACK 标记 |
| G-STD-04.4 | 无硬编码密钥 | **必须** | 搜索密钥模式（见 `clean-state-checklist.md` E04） |

### G-STD-05: REVIEW → VERIFY

**退出门禁 — 进入 VERIFY 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-05.1 | 代码审查已完成且无阻塞问题 | **必须** | 审查报告结论为通过或仅有建议性问题 |
| G-STD-05.2 | 安全问题已审查 | **必须** | 安全审查无 CRITICAL 问题 |
| G-STD-05.3 | 代码风格符合项目规范 | **必须** | Lint 检查 0 错误 |
| G-STD-05.4 | 设计审查通过（如适用） | **建议** | 涉及 UI 或架构变更时需要 |

### G-STD-06: VERIFY → HANDOFF

**退出门禁 — 进入 HANDOFF 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-06.1 | 所有测试通过 | **必须** | 测试命令退出码 0，0 个失败 |
| G-STD-06.2 | 类型检查通过 | **必须** | TypeCheck 退出码 0，0 个错误 |
| G-STD-06.3 | Lint 检查通过 | **必须** | Lint 退出码 0，0 个错误 |
| G-STD-06.4 | 构建成功（如适用） | **必须** | Build 退出码 0 |
| G-STD-06.5 | 验收标准已满足 | **必须** | 对照 G-STD-01.3 的验收标准逐项确认 |

### G-STD-07: HANDOFF → 完成

**退出门禁 — 任务完成声明前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-STD-07.1 | `workflow-state.json` 已更新为 null active_workflow | **必须** | 检查 JSON 文件 |
| G-STD-07.2 | `feature_list.json` 状态和证据已更新 | **必须** | 相关功能 status 为 done，evidence 已填入 |
| G-STD-07.3 | `progress.md` 已完成内容已更新 | **必须** | What's Done 包含本次任务 |
| G-STD-07.4 | `session-handoff.md` 已更新 | **必须** | 包含完成内容、验证证据、下一步建议 |
| G-STD-07.5 | 完成声明已发出 | **必须** | 声明包含：改了哪些文件、跑了哪些检查、原始结果、未验证风险、下一步建议 |

## 三、复杂任务流门禁（Complex Workflow）

> 工作流：`DEEP_INTERVIEW → CONSENSUS_PLAN → TEAM_EXECUTION → QA_SECURITY_REVIEW → RELEASE_HANDOFF`

### G-CPX-01: DEEP_INTERVIEW → CONSENSUS_PLAN

**退出门禁 — 进入 CONSENSUS_PLAN 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-CPX-01.1 | 用户真实意图已提取并确认 | **必须** | 用户确认了意图摘要 |
| G-CPX-01.2 | 边界条件和约束已明确 | **必须** | 记录了技术约束、时间约束、资源约束 |
| G-CPX-01.3 | 非功能需求已讨论 | **必须** | 性能、安全、可用性要求已记录 |
| G-CPX-01.4 | 成功标准已对齐 | **必须** | 用户和代理对"完成"的定义一致 |
| G-CPX-01.5 | 替代方案已评估 | **建议** | 至少讨论了 1-2 个替代方案及其取舍 |

### G-CPX-02: CONSENSUS_PLAN → TEAM_EXECUTION

**退出门禁 — 进入 TEAM_EXECUTION 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-CPX-02.1 | 架构决策已记录（ADR） | **必须** | 至少 1 份 ADR 记录关键架构决策 |
| G-CPX-02.2 | 任务已拆分为独立可并行的工作包 | **必须** | 工作包之间无共享状态冲突 |
| G-CPX-02.3 | 每个子代理的任务边界已定义 | **必须** | 输入、输出、完成标准已明确 |
| G-CPX-02.4 | 子代理数量 ≤ 6 | **必须** | 遵循 AGENTS.md 子代理数量上限 |
| G-CPX-02.5 | 集成点和顺序已规划 | **必须** | 并行任务的结果如何合并已明确 |

### G-CPX-03: TEAM_EXECUTION → QA_SECURITY_REVIEW

**退出门禁 — 进入 QA_SECURITY_REVIEW 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-CPX-03.1 | 所有子代理任务已完成 | **必须** | 每个子代理的输出已收集 |
| G-CPX-03.2 | 集成结果无冲突 | **必须** | 合并后的代码可正确解析 |
| G-CPX-03.3 | 文件一致性检查通过 | **必须** | 无重复定义、无接口不匹配 |
| G-CPX-03.4 | 集成测试通过 | **必须** | 子代理产出的整合体通过基础测试 |

### G-CPX-04: QA_SECURITY_REVIEW → RELEASE_HANDOFF

**退出门禁 — 与标准工作流 G-STD-05 + G-STD-06 合并要求：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-CPX-04.1 | 全面 QA 测试通过 | **必须** | 功能测试 + 回归测试 + 边界测试 |
| G-CPX-04.2 | 全面安全审查通过 | **必须** | 无 CRITICAL 或 HIGH 安全问题 |
| G-CPX-04.3 | 性能基准无退化 | **建议** | 对比实施前后的性能指标 |
| G-CPX-04.4 | 文档已全面更新 | **必须** | API 文档、架构文档、用户指南 |

### G-CPX-05: RELEASE_HANDOFF → 完成

**退出门禁 — 额外于标准 HANDOFF 的要求：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-CPX-05.1 | 发布说明已准备 | **必须** | 变更摘要、影响范围、升级指南 |
| G-CPX-05.2 | 回滚方案已就绪 | **必须** | 明确可逆操作步骤 |
| G-CPX-05.3 | 监控和告警已配置（如适用） | **建议** | 生产部署时需要 |
| G-CPX-05.4 | 干系人已通知 | **建议** | 涉及多团队时 |

> 工作流：`OFFICE_HOURS → CEO_REVIEW → ENG_REVIEW → DESIGN_REVIEW → BUILD → QA → SHIP → RETRO`

**退出门禁 — 进入 CEO_REVIEW 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-PRD-01.1 | 问题定义清晰（解决谁的什么问题） | **必须** | 一句话问题陈述 |
| G-PRD-01.2 | 目标用户画像已定义 | **必须** | 至少 1 个用户角色 |
| G-PRD-01.3 | 价值主张已说明 | **必须** | 用户为什么需要这个功能 |
| G-PRD-01.4 | 市场/竞品简要分析 | **建议** | 类似解决方案及其不足 |

### G-PRD-02: CEO_REVIEW → ENG_REVIEW

|------|------|--------|----------|
| G-PRD-02.1 | 商业可行性已确认 | **必须** | CEO 视角审查通过 |

### G-PRD-04: DESIGN_REVIEW → BUILD

**退出门禁 — 进入 BUILD 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-PRD-04.1 | UI/UX 设计审查通过 | **必须** | 设计师视角审查通过 |

| G-PRD-04.3 | 交互设计已定义 | **必须** | 关键用户流程的交互说明 |
| G-PRD-04.4 | 设计系统对齐 | **建议** | 与现有设计系统一致 |

## 五、TDD 实现流门禁（TDD Workflow）

> 工作流：`BRAINSTORMING → WRITING_PLANS → RED → GREEN → REFACTOR → CODE_REVIEW → VERIFY → FINISH`

### G-TDD-01: BRAINSTORMING → WRITING_PLANS

**退出门禁 — 进入 WRITING_PLANS 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-01.1 | 需求已从多角度探索 | **必须** | 至少考虑了正常路径、边界条件、错误路径 |
| G-TDD-01.2 | 接口契约已草拟 | **必须** | 函数签名、输入类型、输出类型、副作用 |
| G-TDD-01.3 | 测试场景清单已列出 | **必须** | 正面测试 + 负面测试 + 边界测试 |

### G-TDD-02: WRITING_PLANS → RED

**退出门禁 — 进入 RED（写失败测试）前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-02.1 | 实现计划已分步 | **必须** | 每一步对应一个或一组测试 |
| G-TDD-02.2 | 测试框架和工具已确定 | **必须** | 使用项目中已有的测试框架 |
| G-TDD-02.3 | 测试文件路径已确定 | **必须** | 遵循项目测试目录约定 |
| G-TDD-02.4 | 实现步骤不包含"顺便重构" | **必须** | 严格控制范围，不做额外改动 |

### G-TDD-03: RED → GREEN

**退出门禁 — 进入 GREEN（实现代码）前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-03.1 | 测试已编写完成 | **必须** | 至少 1 个测试用例 |
| G-TDD-03.2 | 测试当前全部失败（RED 状态） | **必须** | 运行测试确认失败 |
| G-TDD-03.3 | 测试覆盖了所有预期场景 | **必须** | 对照 G-TDD-01.3 的测试清单 |
| G-TDD-03.4 | 测试本身无逻辑错误 | **必须** | 审查测试代码，确认测试的是正确的行为 |

### G-TDD-04: GREEN → REFACTOR

**退出门禁 — 进入 REFACTOR 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-04.1 | 所有测试通过（100%） | **必须** | 测试运行退出码 0 |
| G-TDD-04.2 | 覆盖率达到目标 | **必须** | 80%+ 覆盖 |
| G-TDD-04.3 | 实现逻辑正确且完整 | **必须** | 对照需求确认无遗漏 |

### G-TDD-05: REFACTOR → CODE_REVIEW

**退出门禁 — 进入 CODE_REVIEW 前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-05.1 | 重构后所有测试仍然通过 | **必须** | 测试运行退出码 0 |
| G-TDD-05.2 | 代码清晰度改善（无过度抽象） | **必须** | 重构后的代码比之前更易读 |
| G-TDD-05.3 | 无新增死代码 | **必须** | 移除未使用的变量、函数、导入 |
| G-TDD-05.4 | 无"顺手重构"越界 | **必须** | 重构范围限于当前功能相关代码 |

### G-TDD-06: CODE_REVIEW → VERIFY

**门禁等同于标准工作流的 G-STD-05：**

参见 [G-STD-05: REVIEW → VERIFY](#g-std-05-review--verify)

### G-TDD-07: VERIFY → FINISH

**门禁等同于标准工作流的 G-STD-06：**

参见 [G-STD-06: VERIFY → HANDOFF](#g-std-06-verify--handoff)

### G-TDD-08: FINISH → 完成

**退出门禁 — 最终完成声明前必须满足：**

| 编号 | 条件 | 严重性 | 验证方法 |
|------|------|--------|----------|
| G-TDD-08.1 | 最终的测试套件全部通过 | **必须** | 包括新测试和已有测试 |
| G-TDD-08.2 | 覆盖率报告达标 | **必须** | 80%+ 行覆盖 |
| G-TDD-08.3 | PR 已准备（含测试结果证据） | **必须** | PR 描述中包含测试通过截图或日志 |
| G-TDD-08.4 | 状态文件已更新 | **必须** | `workflow-state.json`、`feature_list.json`、`progress.md` |

## 六、门禁失败处理协议

### 6.1 门禁失败分类

| 失败类型 | 处理策略 |
|----------|----------|
| **FAIL — 必须条件不满足** | 回退到当前阶段，修复后重新走门禁 |
| **FAIL — 缺少证据** | 补充验证证据后重新判定 |
| **WARNING — 建议条件不满足** | 记录偏差到 `workflow-state.json`，不阻塞推进 |
| **SKIPPED — 门禁不适用** | 记录跳过原因，不视为失败 |

### 6.2 回退规则

```
回退距离 = 1 阶段（默认）

特殊情况可回退多阶段：
  - 发现需求理解错误 → 回退到 INTAKE
  - 发现架构设计错误 → 回退到 PLAN
  - 发现测试策略错误 → 回退到 RED
```

### 6.3 门禁记录格式

在 `workflow-state.json` 的 `phase_gate_status.gates` 中记录：

```json
{
  "gate_id": "G-STD-04",
  "gate_name": "EXECUTE → REVIEW",
  "result": "PASS",
  "timestamp": "2026-06-09T14:30:00+08:00",
  "verifier": "code-reviewer",
  "details": {
    "all_steps_executed": true,
    "syntax_errors": 0,
    "todos_remaining": 0,
    "secrets_found": false
  },
  "notes": "所有计划步骤已完成，代码无语法错误"
}
```
