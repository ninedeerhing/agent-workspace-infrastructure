# 大型项目扩展指南

> **适用场景**：当项目规模突破单文件/单代理能力边界时，参照本指南升级工作流和架构。

---

## 1. 工作流升级决策矩阵

| 当前规模               | 使用工作流           | 升级信号                                   |
| ---------------------- | -------------------- | ------------------------------------------ |
| ≤ 10 文件、单模块      | Default Workflow     | —                                          |
| > 10 文件、跨模块改动  | Complex Workflow     | 一次 PR 触及 10+ 文件                      |
| 多代理协同             | Complex + Team       | 独立子任务可并行、单开发者耗时 > 2h        |
| 多目标、长期项目       | OMX Standard + Ultragoal | 任务跨会话存在、需持久化目标跟踪        |
| 高风险架构变更         | Prometheus Strict    | 涉及安全边界、核心数据模型、API 契约       |

**升级原则**：上一级工作流的信号出现 2 个以上再升级，避免流程膨胀。

## 2. OMX Standard 触发条件

当项目同时满足以下 ≥ 2 项时，从 Default Workflow 切换到 OMX Standard：

- 目标数 ≥ 3 且相互依赖
- 项目预期持续 ≥ 4 周
- 需要 `deep-interview → ralplan → ultragoal` 全链条
- 从会话上下文频繁丢失（单次对话不足以覆盖全部上下文）

**关键路径**：
```
deep-interview → ralplan（共识规划）→ ultragoal（持久化目标跟踪）→ team-pipeline（并行执行）→ verification → handoff
```

## 3. 代理分派策略

- 单开发者环境下并行代理上限：**4 个**（硬上限 6 个）
- 代理间无共享状态——通过 leader 传递明确输入/输出契约
- 每个代理消耗约 15%-25% 上下文窗口，**余量始终 ≥ 25%** 给整合阶段
- 通信开销估算：每增加 1 个子代理 ≈ +30% 协调成本
- 分派决策优先级：独立可验证 > 可并行 > 无文件冲突 > 领域专业匹配

## 4. 多模块项目结构

| 模式        | 适用场景                               | 注意点                           |
| ----------- | -------------------------------------- | -------------------------------- |
| Monorepo    | 团队 ≤ 20 人，模块间共享代码频繁       | 统一版本号、统一 CI/CD           |
| Multi-repo  | 团队 > 20 人，模块独立部署、独立版本   | 接口契约先行、集成测试集中管理   |
| 混合模式    | 核心模块 monorepo + 独立服务 multi-repo | 共享代码通过内部包管理           |

**共享代码管理**：抽取到 `packages/shared`，语义化版本控制，变更必须通过集成测试。

## 5. 技术债务管理

- **清理节奏**：每完成 5 个功能，触发一次 `$ai-slop-cleaner` 扫描
- **重构预算**：每个冲刺预留 20% 工时给技术债务偿还
- **债务登记**：所有已知债务写入 `harness/tech-debt.md`，标注影响范围和偿还计划
- **禁止积累**：同一模块连续 2 个冲刺留下债务 → 下一个冲刺必须清零

## 6. 上下文窗口管理

| 阶段       | 上下文策略                             | 窗口使用上限 |
| ---------- | -------------------------------------- | ------------ |
| 调研阶段   | 分模块加载，每模块独立会话             | 60%          |
| 规划阶段   | 加载核心规范 + 目录结构，禁用无关上下文 | 50%          |
| 执行阶段   | 每次只加载被修改文件 + 直接依赖        | 70%          |
| 整合阶段   | 加载变更摘要（非全量文件）             | 80%          |

**分片策略**：

- 大型代码库按功能域切分上下文：`packages/auth/`、`packages/payment/` 独立加载
- 使用 `$omc-conversation-continuity` 在对话使用 70% 窗口时触发交接
- 每次交接生成结构化摘要（已变更文件清单 + 待办事项 + 阻塞项）
- 不使用最后 20% 上下文窗口做关键架构决策

## 7. 撤离路线

如果发现工作流过度复杂化（流程开销 > 产出价值）：

1. 降级到 Default Workflow，保留 `harness/progress.md` 追踪
2. 关闭非必要的并行代理
3. 合并微模块为少而大的模块（逆向拆分）
4. 删除无实际使用的规范文件（不以 "可能有用" 为由保留）
