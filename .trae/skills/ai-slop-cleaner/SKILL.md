# AI Slop Cleaner — AI 生成代码清理
## 定位
在不改变功能行为的前提下，系统性地清除 AI 生成代码中的常见冗余模式（slop）。专注于简化表达、删除冗余、收紧边界——不做功能变更。
## 触发条件
- 用户明确说 `deslop`、`anti-slop`、`AI slop`、`cleanup slop`
- 需要清理啰嗦、重复、过度抽象的代码
- 后续实现留下了重复逻辑、死代码、包装层、边界泄漏
- 目标是简化和清理，不是新功能交付
## 不适用场景
- 主要是新功能构建或产品变更
- 用户想要大范围重新设计而非增量清理
- 普通重构请求（无简化/反 slop 意图）
- 行为不明确且无法用测试保护
## 核心原则
1. **保护行为**：除非用户明确要求，否则不改变功能行为
2. **测试先行**：在编辑代码之前，先用回归测试锁定行为
3. **删除优先**：优先删除冗余代码，而非添加新抽象
4. **复用优先**：复用现有工具和模式，不引入新模式
5. **小步前进**：保持差异小、可回滚、聚焦单一气味
6. **不新增依赖**：除非用户明确要求
## 常见 Slop 模式分类
### 1. 重复逻辑（Duplication）
- 复制粘贴的代码分支
- 冗余的辅助函数
- 跨文件的相同逻辑块
- 多个文件中的相同错误处理模式
### 2. 死代码（Dead Code）
- 未被引用的函数/类/变量
- 不可达分支
- 过时的功能开关
- 调试残留（console.log、debug 语句）
- 未使用的 import
### 3. 不必要的抽象（Needless Abstraction）
- 直通包装层（只转发调用的函数/类）
- 投机性的间接层
- 单次使用的辅助层
- 过度接口化（只有一个实现的接口）
### 4. 边界违规（Boundary Violations）
- 隐藏的耦合
- 错位的职责
- 跨层 import 或副作用
- 模块间不恰当的依赖方向
### 5. 防御性过度（Over-Defensive Code）
- 对不可能出现的 null/undefined 的过度检查
- 多余的 try-catch 包装
- 永远不会触发的默认分支
- 冗余的类型守卫
### 6. 过度注释（Over-Commenting）
- 代码自解释的情况下添加的注释
- 表意注释
- 明显的参数说明注释
- TODO/FIXME 僵尸注释（已解决但未删除）
### 7. UI/设计默认值（UI/Design Defaults）
- 通用的 AI 蓝色/紫色调色板（如 #3B82F6）
- 所有元素上多余的 box-shadow
- 过度统一的 3/4 列网格布局
- 不必要的极端渐变
- 重复的标题/描述段落堆砌
## 执行流程
### 第 1 步：保护当前行为
- 识别必须保持不变的代码行为
- 在编辑之前运行或编写最窄的回归测试
- 如果无法先写测试，明确记录验证计划
### 第 2 步：编写清理计划
- 限定清理范围为指定文件或功能区域
- 列出具体要清除的气味
- 按从最安全（删除死代码）到最风险（合并重复）排序
### 第 3 步：分类后逐 Pass 清理
严格按以下顺序执行，不捆绑不相关的重构：
| Pass | 内容 | 风险 |
|------|------|------|
| Pass 1 | 死代码删除 | 低——删除不执行代码 |
| Pass 2 | 重复移除 | 中——需确认行为一致 |
| Pass 3 | 命名和过度注释清理 | 低——不影响行为 |
| Pass 4 | 不必要抽象平铺 | 高——需确认等价 |
| Pass 5 | 边界修正 | 高——影响依赖关系 |
| Pass 6 | 测试加固 | 加固已有行为 |
每次 Pass 后运行验证，确认行为不变。
### 第 4 步：质量门控
- 回归测试保持绿色
- 运行相关 lint、类型检查
- 运行已触及区域的单元/集成测试
- 运行可用的静态/安全检查
- 如果门控失败，修复问题或回退有风险的清理
### 第 5 步：证据报告
始终报告：
- 更改的文件
- 简化内容：删除了什么、合并了什么
- 行为锁定：哪些测试保证了行为不变
- 剩余风险：哪些风险仍未验证
## 审查模式（--review）
审查模式是清理工作完成后独立的审查 Pass，维护编写者/审查者分离。
审查模式步骤：
1. 不开始编辑文件
2. 审查清理计划和更改的文件
3. 专门检查：
   - 遗留的死代码或未使用的导出
   - 本应合并但未合并的重复逻辑
   - 仍然模糊边界的包装层或抽象
   - 缺失的测试或弱验证
   - 看起来无意中改变了行为的清理
4. 生成审查裁定，附带必要的后续修复
5. 将需要修改的内容交还给独立的编写 Pass
## 反模式 / 红牌
| 反模式 | 说明 |
|--------|------|
| 清理时改变功能行为 | 红牌。保持行为不变是核心原则 |
| 跳过回归测试 | 红牌。必须先锁定行为 |
| 不写清理计划直接编辑 | 红牌。必须先分类再逐 Pass 执行 |
| 一次编辑捆绑多种 slop | 黄牌。多个不相关清理应分开 Pass |
| 引入新依赖或新抽象 | 黄牌。清理应以删除为主 |
| 扩展到用户未要求的功能 | 黄牌。不扩大清理范围 |
| 自己写自己审 | 黄牌。高风险清理用 --review 模式 |
## 成功标准
- 功能行为与清理前完全一致
- 回归测试全部通过
- 代码行数减少（删除多于新增）
- 每个 Pass 后可独立验证
- 生成了包含更改文件和剩余风险的证据报告
