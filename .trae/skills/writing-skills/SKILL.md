# Writing Skills — 编写技能（元技能）

## 定位

这是一个**元技能**——用 TDD 的方法论来编写技能本身。技能是指导 AI 行为的提示词文档，编写技能就是编写高质量的提示词。

## 触发条件

- 用户要求创建新技能
- 用户要求更新或修改现有技能
- 用户要求改善某个技能的效果

## TDD 方法编写技能

### RED（观察失败）

1. 在没有技能的情况下，尝试执行目标任务
2. 观察 AI 在哪里做错了、遗漏了什么、偏离了什么
3. 记录具体的失败模式——这些就是技能需要解决的问题
4. 例：没有 brainstorming 技能时，AI 直接写代码 → 设计不周全

### GREEN（最小技能）

1. 写一个**刚好足够**解决观察到失败的最小技能
2. 包含：触发条件、核心步骤、关键原则
3. 不要一开始就写完整的复杂技能
4. 用最小技能重新测试同样的任务，观察改善

### REFACTOR（堵塞借口）

1. 用最小技能测试后，观察还有什么失败或偏差
2. 识别 AI 可能用来规避技能的借口：
   - "任务太简单不需要这个技能"
   - "我已经理解需求了不需要设计"
   - "这个步骤可以跳过"
3. 在技能中添加**红牌**和**硬性门控**来堵住这些借口
4. 例如：`brainstorming` 的 HARD-GATE："在任何创造性工作之前必须加载"

## 技能文件结构

每个 SKILL.md 必须包含：

```yaml
---
name: skill-name
description: 仅包含触发条件，不包含工作流摘要。当xxx时使用。
---
```

### description 陷阱

**错误**：
```yaml
description: 用于brainstorming，包含9步检查和设计文档输出。
```
这暴露了工作流细节，AI 会跳过加载直接执行。

**正确**：
```yaml
description: 在任何创造性工作之前必须使用。触发条件：用户要求实现新功能、构建组件、添加能力、修改行为。
```
只描述"何时使用"，不描述"里面有什么"。

### 正文结构

1. **定位**：一句话说明技能在流程中的位置
2. **铁律**（如有）：不可违反的硬性规则
3. **触发条件**：何时加载这个技能
4. **核心原则**：3-5 条指导原则
5. **步骤/流程**：清晰的步骤分解
6. **反模式/红牌表**：禁止的行为和常见错误
7. **成功标准**：如何判断技能执行成功
8. **输出物**：技能完成后应产出什么

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| description 含工作流 | 红牌。description 只能含触发条件 |
| 没有硬性门控 | 黄牌。关键技能需要 HARD-GATE |
| 步骤过于笼统 | 黄牌。步骤应具体可执行 |
| 缺少反模式表 | 黄牌。每个技能都应有反模式表 |
| 直接写完整版 | 黄牌。遵循 RED→GREEN→REFACTOR 迭代 |
