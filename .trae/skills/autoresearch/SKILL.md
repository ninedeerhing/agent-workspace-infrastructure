# Autoresearch — 有界验证器门控研究

## 铁律

> **NO FINDINGS WITHOUT EVIDENCE. NO DEEPER DIVE WITHOUT VERIFICATION.**
> 没有证据不得声称发现。未通过验证门不得深入下一层。

## 定位

研究不是随意浏览代码或文档，而是有边界、有节奏、有验证的科学探索。本技能强制三阶段研究流程，每阶段之间设置验证门，确保研究的深度、广度和质量均在可控范围内，产出可追溯的证据链。

## 触发条件

- 需要调研不熟悉的代码库模块
- 需要理解第三方库/框架的工作原理
- 需要分析系统间依赖关系和数据流
- 需要回答"这个系统怎么工作"类问题
- 需要在实现前确认技术可行性
- 需要为架构决策收集事实证据

## 核心概念

### 有界（Bounded）

研究必须有明确边界，防止陷入无限深挖：

| 边界维度 | 说明 | 示例 |
|----------|------|------|
| **范围边界** | 研究哪些模块/文件/概念 | "只研究数据持久化层，不涉及 API 层" |
| **深度边界** | 最多追溯几层调用/依赖 | "最多追溯 3 层调用链" |
| **时间边界** | 单阶段最长时间盒 | "表层扫描不超过 10 分钟" |
| **产出边界** | 最终交付物的格式和粒度 | "产出调用链图 + 关键文件列表" |

### 验证器门控（Verifier-Gated）

每个阶段结束后设置验证门，只有通过验证才能进入下一阶段：

```
阶段 N → 验证门 N → (通过) → 阶段 N+1
                   → (失败) → 回到阶段 N 补充或调整边界
```

验证门检查项：
- 发现是否有具体证据（文件:行号 / URL）
- 证据是否可复现（他人能否找到同一处证据）
- 发现是否自洽（无内部矛盾）
- 覆盖度是否足够（是否遗漏关键路径）

## 三阶段流程

### 阶段 0：边界定义（Boundary Definition）

**必须先完成阶段 0，才能开始任何研究操作。**

步骤：
1. **明确研究目标**：用一句话描述要回答什么
2. **划定范围**：列出要研究的文件/模块/概念，以及明确排除的部分
3. **设定深度上限**：最多追溯 N 层调用/依赖
4. **设定时间盒**：每个阶段的时间上限
5. **定义成功标准**：什么产出算研究完成

输出物：
- 研究目标陈述（一句话）
- 范围清单（纳入 + 排除）
- 深度上限值
- 时间分配表
- 成功标准列表

**红牌**：以下情况不得进入阶段 1：
- 研究目标模糊（无法用一句话说清）
- 无明确排除项（什么都想看 = 什么都看不清）
- 无深度上限（默认设为 3）
- 无时间盒（默认每阶段 10 分钟）

### 阶段 1：表层扫描（Surface Scan）

**目标**：快速建立全局认知，识别关键文件和核心概念。

研究操作：
1. **目录结构概览**：列出相关目录的文件树
2. **入口发现**：找到入口文件、主模块、配置文件
3. **符号索引**：识别核心类/函数/接口名称
4. **依赖识别**：列出关键的 import / require / 依赖声明
5. **文档速览**：阅读 README、关键注释、JSDoc/Docstring

产出物：
- 关键文件列表（按重要性排序）
- 核心符号表（类/函数/接口 → 所在文件）
- 依赖概览图（直接依赖关系）
- 未解问题列表（待阶段 2 深入的问题）

---

### 验证门 1：表层验证（Surface Verification）

**通过条件**（必须全部满足）：

| 检查项 | 验证方式 | 
|--------|----------|
| 每个"关键文件"都有路径证据 | 列出文件绝对路径 |
| 每个"核心符号"都有位置证据 | 列出文件:行号 |
| 依赖关系有代码证据 | 列出 import/require 语句所在行 |
| 覆盖度检查：是否遗漏了明显的入口或配置 | 对照目录树检查 |
| 无内部矛盾：不同来源的信息一致 | 交叉验证关键发现 |

**不通过时的处理**：
- 返回阶段 1，补充遗漏的证据
- 如果发现范围边界不合理，回到阶段 0 调整边界

---

### 阶段 2：深度探索（Deep Dive）

**目标**：在表层基础上，追溯调用链、理解数据流、验证假设。

研究操作：
1. **调用链追踪**：从入口函数出发，向下追溯至深度上限
2. **数据流分析**：追踪关键数据从输入到输出的完整变换链
3. **条件分支映射**：识别关键的条件判断和分支逻辑
4. **配置影响分析**：配置项如何影响运行时行为
5. **错误路径探索**：异常处理和边界情况的处理方式

产出物：
- 调用链图（入口 → N 层深度）
- 数据流文档（数据从哪来 → 经过什么变换 → 到哪去）
- 关键决策点列表（条件判断 → 分支走向）
- 边界条件汇总（null/空/超大/超时等情况的处理）

---

### 验证门 2：深度验证（Deep Verification）

**通过条件**（必须全部满足）：

| 检查项 | 验证方式 |
|--------|----------|
| 调用链每步都有代码证据 | 列出每个调用点的文件:行号 |
| 数据流完整闭环 | 输入到输出无断点 |
| 分支逻辑可复现 | 给定输入可预测走哪个分支 |
| 交叉验证通过 | 核心结论被至少 2 处独立证据支撑 |
| 深度未超上限 | 追溯层数 ≤ 边界定义中的深度上限 |

**不通过时的处理**：
- 补充缺失的证据链环节
- 修正矛盾的理解
- 如果交叉验证失败，怀疑单点证据的可靠性
- 若触及深度上限但仍有重要路径未探索，记录为"已知未知"

---

### 阶段 3：综合输出（Synthesis）

**目标**：将研究发现转化为结构化、可消费的输出。

必须产出的内容：
1. **执行摘要**：一到两段话概括核心发现
2. **架构概览图**：用 ASCII/文本绘制的模块关系图（至少含 3 个模块）
3. **关键文件清单**：表格，含路径、职责、重要性评级
4. **核心调用链**：从入口到关键节点的完整路径
5. **已知未知**：因边界限制未能探索的重要问题
6. **风险与建议**：发现的潜在问题和改进机会

---

### 验证门 3：输出验证（Output Verification）

**通过条件**（必须全部满足）：

| 检查项 | 验证方式 |
|--------|----------|
| 执行摘要可独立理解 | 无"如上所述"等依赖前文的引用 |
| 所有断言有证据链 | 每个技术断言都能追溯到验证门 1/2 中的证据 |
| 已知未知诚实标注 | 未探索区域明确标注 |
| 无过度推断 | 区分"代码做了什么"和"推测为什么这样做" |
| 产出物完整 | 6 类产出物全部包含 |

---

## 并行研究模式

当研究目标涉及多个独立模块时，可启用并行模式：

1. 阶段 0 仍为统一边界定义
2. 阶段 1 可为每个模块并行执行（子代理各自扫描不同模块）
3. 验证门 1 需汇总所有子代理的证据后统一验证
4. 阶段 2 按需并行或串行（取决于模块间是否有依赖）

**约束**：
- 最多 3 个并行研究分支
- 每个分支有独立的时间盒
- 汇总阶段必须交叉验证不同分支的发现一致性

## 研究三档

| 档位 | 目标深度 | 适用场景 | 单阶段时间盒 |
|------|----------|----------|--------------|
| **Quick** | 深度 1-2 层 | 小模块（<10 文件）、简单 API、已有部分了解 | 5 分钟 |
| **Standard** | 深度 2-3 层 | 中型模块（10-30 文件）、跨 2-3 个服务 | 10 分钟 |
| **Deep** | 深度 3-5 层 | 大型系统（30+ 文件）、跨团队边界、安全/性能敏感 | 15 分钟 |

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 无边界就开始研究 | 红牌。必须先定义边界（阶段 0） |
| 跳过验证门 | 红牌。每阶段结束必须通过验证门 |
| 仅凭记忆声称发现 | 红牌。所有发现必须有文件:行号或 URL 证据 |
| 无限深挖 | 红牌。触达深度上限后必须停止，记录为"已知未知" |
| 不产出结构化报告 | 黄牌。研究结束必须产出 6 类交付物 |
| 单点证据断言 | 黄牌。关键结论应有交叉验证 |
| 混入个人推测 | 黄牌。必须区分"代码做了什么"和"推测为什么" |
| 超过时间盒不停止 | 黄牌。到时间必须输出当前发现，记录未完成项 |
| 范围蔓延 | 红牌。研究过程中发现"应该也看看X"，必须更新边界定义后才能继续 |

## 与其他技能的协作

| 前置技能 | 关系 |
|----------|------|
| `$deep-interview` | 当研究目标不清晰时，先用深度访谈澄清 |
| `$brainstorming` | 研究结果可作为头脑风暴的事实输入 |
| `$writing-plans` | 研究产出直接输入到实现计划阶段 |

| 后置技能 | 关系 |
|----------|------|
| `$systematic-debugging` | 研究过程中发现 bug 时可切换到调试流程 |
| `$code-review` | 研究产出可作为代码审查的参考基线 |
| `$executing-plans` | 研究完成后的实现计划可直接执行 |
