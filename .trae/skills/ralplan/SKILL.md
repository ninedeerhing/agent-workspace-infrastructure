# Ralplan — 共识规划

## 定位

通过 Planner → Architect → Critic 三角循环达成共识的技术规划。每个角色独立审查和挑战方案，最多 5 轮迭代，最终产出架构决策记录（ADR）。

## 触发条件

- `deep-interview` 已完成
- 需要制定技术方案
- 涉及架构决策
- 有多个可行方案需要评估

## 三角角色

| 角色 | 职责 | 关注点 |
|------|------|--------|
| **Planner** | 制定方案 | 可行性、步骤、时间线 |
| **Architect** | 审查架构 | 非功能需求、扩展性、技术债务 |
| **Critic** | 挑战假设 | 风险、盲点、替代方案 |

## 执行流程

### 第 1 轮：Planner 初稿

- Planner 基于需求制定初始方案
- 包含：技术选型、架构草图、实现步骤、风险评估

### 第 2 轮：Architect 审查

- Architect 审查方案的非功能维度：
  - 可扩展性
  - 性能
  - 安全性
  - 可维护性
  - 可测试性
  - 技术债务预算
- 提出修改建议

### 第 3 轮：Critic 挑战

- Critic 从对立面挑战：
  - 假设是否成立？
  - 有没有更简单的方案？
  - 最大的风险是什么？
  - 如果关键人离开怎么办？
- 要求 Planner 回应每个挑战

### 第 4 轮：整合修订

- Planner 整合 Architect 和 Critic 的反馈
- 修订方案，标注修改点和原因

### 第 5 轮：终审

- Architect 和 Critic 快速最终审查
- 确认所有关键问题已解决
- 产出 ADR

## ADR 输出格式

```markdown
# ADR: [决策标题]

## 状态
[提议 / 已接受 / 已废弃 / 已取代]

## 上下文
[为什么需要做这个决策]

## 决策
[选择了什么方案]

## 后果
### 正面
- ...
### 负面
- ...
### 风险
- ...
```

## 迭代控制

- 最少 2 轮，最多 5 轮
- 每轮必须有实质性的反馈或修改
- 如果连续 2 轮无新观点，自动结束
- Critic 必须提出至少 3 个挑战

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 跳过 Architect 审查 | 红牌。非功能需求必须有人审查 |
| Critic 只提正面反馈 | 红牌。Critic 必须挑战 |
| 无限迭代 | 红牌。最多 5 轮 |
| 不定稿 ADR | 红牌。最终必须有 ADR 输出 |
| Planner 兼任其他角色 | 黄牌。三角角色应独立 |
