# OMO Agent Router — 代理路由器
## 定位
本技能是 OMX 工作区的"智能调度中心"。它分析任务特征，匹配最适合的代理能力，做出路由决策，并管理代理资源分配。在单代理场景下作为自我能力审视工具，在多代理场景下作为任务分配协调层。
## 触发条件
- 用户提出任务，需要判断应委派给哪个代理/技能
- 多代理协作场景中需要统一的任务分配决策
- 当前代理不确定是否自己能胜任任务
- 需要优化代理资源分配和负载均衡
- 任务链需要多个技能协作，需要规划路由顺序
## 不触发条件
- 任务明确且简单，不需要路由决策 → 直接执行
- 用户已明确指定代理/技能 → 直接使用指定技能
- 仅需加载单个技能 → 直接加载该技能

## 执行流程
### 第 1 步：分析任务特征
从任务描述中提取特征向量：
| 特征维度 | 可选值 | 提取方式 |
|----------|--------|----------|
| **复杂度** | simple / medium / complex / critical | 涉及文件数、依赖广度、风险等级 |
| **领域** | code / architecture / research / quality / ops / product | 关键词匹配 + 上下文推断 |
| **操作类型** | create / modify / analyze / fix / review / plan / deploy | 动词分析 |
| **紧急度** | low / medium / high / critical | 用户表述 + 阻塞影响 |
| **独立性** | standalone / has_dependencies | 是否依赖其他未完成工作 |
| **歧义度** | clear / partially_clear / ambiguous | 需求描述的完整程度 |
| **安全敏感** | yes / no | 是否涉及凭证、权限、敏感数据 |
### 第 2 步：计算匹配分数
对每个候选代理/技能计算匹配分数：
```
MATCH_SCORE = 领域匹配 × 0.30
            + 操作匹配 × 0.25
            + 复杂度适配 × 0.20
            + 可用性 × 0.15
            + 历史成功率 × 0.10
```
**匹配规则**：
- **领域匹配**：完全匹配=1.0，相关领域=0.6，无关=0.0
- **操作匹配**：完全匹配=1.0，可执行但有更优选择=0.5，不匹配=0.0
- **复杂度适配**：代理擅长该复杂度=1.0，可处理=0.7，勉强=0.3，不适合=0.0
- **可用性**：空闲=1.0，轻度负载=0.7，中度负载=0.4，重度负载=0.0
### 第 3 步：做出路由决策
根据匹配分数和场景规则做出决策：
#### 决策规则
1. **最高分原则**：默认选择匹配分数最高的代理/技能
2. **分数阈值**：最高分 < 0.4 时，建议用户手动指定
3. **分数接近**：前两名分数差距 < 0.1 时，考虑组合路由
4. **安全优先**：安全敏感任务优先路由到 `security-reviewer`（即使分数略低）
5. **规划先行**：歧义度=ambiguous 时，优先路由到 `$deep-interview` 或 `$brainstorming`
#### 路由模式
| 模式 | 场景 | 路由策略 |
|------|------|----------|
| **直接路由** | 任务明确匹配单个代理 | 单一代理/技能 |
| **链式路由** | 任务需要多个阶段 | 顺序路由：A → B → C |
| **并行路由** | 任务可拆分为独立子任务 | 并行分派到多个代理 |
| **条件路由** | 路由取决于前置结果 | A 完成后根据结果选择 B 或 C |
| **回退路由** | 主代理失败/不可用 | 主代理 → 备用代理 |
### 第 4 步：验证路由决策
- [ ] 选中的代理/技能的能力是否覆盖任务所有需求？
- [ ] 是否考虑了任务的安全敏感性？
- [ ] 是否有更简单的路径（不过度路由）？
- [ ] 代理当前是否可用（无阻塞/过载）？
- [ ] 链式路由的每个环节是否都有明确的输入/输出？
- [ ] 并行路由的子任务之间是否真正独立（无共享状态冲突）？
### 第 5 步：输出路由计划
按模板生成结构化的路由计划（见下方模板）。
## 路由计划模板
```markdown

- **复杂度**: [simple/medium/complex/critical]

- **操作类型**: [create/modify/analyze/fix/review/plan/deploy]
- **紧急度**: [low/medium/high/critical]
- **独立性**: [standalone/has_dependencies]
- **歧义度**: [clear/partially_clear/ambiguous]
- **安全敏感**: [yes/no]
### 路由决策
```

## 路由简化规则（防止过度路由）
以下场景**不启动**路由流程，直接执行：
1. 单文件简单修改（< 20 行变更）
2. 用户已明确指定代理/技能
3. 纯信息查询（无代码变更）
4. 单个已有的简单命令执行
5. 对话中的快速确认/回复（非任务型）
**简化路由检查**：如果以下 3 项全部为 "否"，则跳过路由：
- [ ] 涉及 3+ 文件变更？
- [ ] 需要 2+ 不同领域的能力？
- [ ] 存在安全/性能/架构风险？
## 反模式 / 红牌
| 反模式 | 严重性 | 说明 |
|--------|--------|------|
| 跳过路由分析直接执行 | **FATAL** | 涉及多代理或复杂任务时必须路由分析 |
| 安全敏感任务忽略安全审查 | **FATAL** | 安全敏感任务必须路由安全审查环节 |
| 过度路由 | **FATAL** | 简单任务不应启动重量级路由流程 |
| 路由无证据 | **FATAL** | 路由决策必须有特征分析和分数计算依据 |
| 忽略代理可用性 | **FATAL** | 将任务路由到已阻塞/过载的代理 |
| 并行子任务有共享状态 | **FATAL** | 并行路由的子任务必须真正独立 |
| 不记录路由日志 | **WARNING** | 路由决策应记录供后续分析 |
| 链式路由无输出定义 | **WARNING** | 每个环节必须有明确的输入和预期输出 |
