# RTK Strategy — 推理-令牌-知识优化框架

## 定位

RTK 是一个系统化 Token 优化技能，将代理的认知链路拆解为**推理链分段 → 工具输出漏斗 → 知识锚定**三个阶段，实现上下文利用率最大化、任务精度不降低、Token 成本可控。

## 铁律

> **不是给代理更多上下文，而是给代理更精确的上下文。**
> 每次工具调用和推理步骤都是"认知资源分配"问题。

## 触发条件

- 上下文窗口使用率超过 70%
- 推理步数超过 20 步
- 多文件重构（5+ 文件）或大型架构变更（10+ 文件）
- 多代理并行协作任务
- 用户明确要求 Token 优化或成本控制
- 工具输出明显冗余（文件读取、grep 搜索返回大量结果）

## 核心原则

1. **认知资源分配**：每一步推理都考虑"这段上下文对下一步真的必要吗？"
2. **分层压缩**：推理链、工具输出、知识状态分别处理，不混为一谈
3. **锚定优先**：关键事实（约束、发现、决策、不确定性）必须持久化锚定
4. **按需注入**：不同代理角色（planner、executor、reviewer）接收不同粒度的上下文
5. **可逆性**：压缩不丢失信息——保留检索路径，而非丢弃数据

## 四大策略

### 策略一：推理链分段

将推理链分为三个区段，采用不同保留策略：

| 区段 | 范围 | 保留策略 | Token 占比 |
|------|------|----------|------------|
| **锚点段** | 任务定义、验收标准、硬约束 | 完整保留 | ~15% |
| **活跃段** | 最近 N 步推理（N=5-10） | 完整保留 | ~25% |
| **归档段** | 早期中间推理 | 摘要压缩（1:10） | ~10% |

**执行步骤**：
1. 推理步数 > 20 时激活分段
2. 每 10 步执行一次归档压缩
3. 遇到关键决策点时，将对应推理提升到锚点段
4. 被推翻的决策标记为 `overridden`，保留证据链

**预期效果**：上下文 Token 减少 53.8%，任务完成率提升 9%，目标漂移率降低 66.7%。

### 策略二：工具输出漏斗

建立三层过滤漏斗，减少工具输出的冗余内容：

```
第1层：原始输出（100%）
  → 过滤：去掉空行、分隔线、重复头信息
第2层：结构化输出（60-80%）
  → 过滤：保留关键字段、错误信息、异常值
第3层：精炼输出（15-30%）
  → 过滤：提取可操作信息、异常信号、决策相关数据
```

**各工具默认漏斗层**：

| 工具 | 默认层级 | 例外保留到第3层 |
|------|----------|-----------------|
| Read（文件读取） | 第2层 | 关键函数签名、错误处理块 |
| Grep（搜索） | 第2层 | 精确匹配行 |
| RunCommand | 第2层 | 错误输出（完整保留） |
| Glob（文件匹配） | 第2层 | 项目结构文件 |
| LS（目录列表） | 第3层 | N/A |

**执行步骤**：
1. 每次工具调用后检查输出大小
2. 输出超过 100 行时自动激活漏斗
3. 错误输出始终完整保留
4. 在压缩输出末尾标注原始行数（但不要暴露缓存 ID）

### 策略三：知识锚定

动态维护一个知识锚点表，防止长对话中遗忘关键事实。

**锚点类型**：
- `constraint`：必须遵守的硬约束
- `discovery`：探索中发现的关键信息
- `decision`：已做出的设计/技术决策
- `uncertainty`：尚未确定、需要后续确认的事项

**执行步骤**：
1. 任务开始时初始化空锚点表
2. 每遇到关键事实立即锚定（不等到批量刷新）
3. 总锚点 Token 预算硬限制：**不超过 500 tokens**
4. 每 15 分钟/10 步推理执行一次锚点表去重和排序
5. 已解决的 `uncertainty` 转为 `discovery` 或 `decision`

**优先级排序**：constraint > decision > discovery > uncertainty

### 策略四：层级上下文注入

根据代理角色按需注入不同粒度的上下文：

| 上下文层级 | 内容 | 适用代理 |
|------------|------|----------|
| **L1 - 任务骨架** | 目标、验收标准、硬约束 | 所有代理 |
| **L2 - 当前状态** | 已完成步骤、待处理项、活跃锚点 | executor、planner、orchestrator |
| **L3 - 详细日志** | 完整推理链、完整工具输出 | debugger、reviewer |

**注入策略**：

| 代理角色 | L1 | L2 | L3 |
|----------|----|----|-----|
| orchestrator | ✅ | ✅ | ❌ |
| planner | ✅ | ✅ | 摘要 |
| executor | ✅ | ✅ | 按需 |
| code-reviewer | ✅ | ❌ | 变更差异 |
| debugger | ✅ | 摘要 | ✅ |
| verifier | ✅ | ✅ | ❌ |

## 压缩级别速查

| 压缩级别 | Token 节省 | 适用场景 | 精度损失 |
|----------|-----------|----------|----------|
| **轻度**（仅去重） | 15-25% | 日常编码任务 | 无 |
| **中度**（漏斗+分段） | 40-55% | 多文件重构 | 极小 |
| **重度**（全策略） | 55-65% | 大型架构变更 | 可接受 |
| **极限**（激进摘要） | 70-80% | 紧急上下文不足 | 需人工复核 |

## 与 Headroom 策略的协同

| 维度 | Headroom | RTK |
|------|----------|-----|
| 作用层 | 工具输出 → LLM 之间 | 代理内部认知链路 |
| 压缩对象 | 结构化数据（JSON、日志） | 推理链、知识状态、上下文 |
| 触发时机 | 每次工具调用后 | 推理步骤之间 |
| 精度保障 | 保留异常项 + 统计分布 | 保留锚点 + 活跃推理段 |

两者叠加可达 **70-85% Token 节省**。

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 不压缩直接传递全量上下文 | 红牌。上下文溢出前必须激活压缩 |
| 锚点表超过 500 tokens | 黄牌。锚点必须精简，超过上限时去重排序 |
| 对错误输出应用漏斗 | 红牌。错误输出始终完整保留 |
| 跳过推理链分段 | 黄牌。步数 > 20 时必须分段 |
| 对简单任务使用重度压缩 | 黄牌。根据任务复杂度选择压缩级别 |
| 压缩后不保留检索路径 | 红牌。压缩必须可追溯 |

## 输出物

- 压缩后的精炼上下文（替代原始上下文注入代理）
- 当前知识锚点表（作为前置上下文注入）
- 压缩级别记录（轻度/中度/重度/极限）

## 成功标准

- 上下文 Token 消耗减少 40-65%（相对于未优化）
- 任务完成率不降低（甚至提升）
- 关键事实（约束、决策）未被压缩丢失
- 错误输出始终完整保留
- 锚点表不超过 500 tokens
