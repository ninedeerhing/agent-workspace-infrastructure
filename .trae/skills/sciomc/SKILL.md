# Sciomc — 并行科学家编排

## 定位

将复杂研究目标分解为多个独立维度，并行分派多个 scientist 代理进行调查，然后进行交叉验证与综合结论。适用于需要从多角度同时分析一个复杂问题的场景。

## 触发条件

- 用户提到 `sciomc`、`parallel research`、`multi-analysis`
- 需要对代码库进行多维度并行分析
- 研究目标可分解为多个独立调查方向
- 需要交叉验证才能得出可靠结论

## 核心原则

1. **独立分解**：研究维度之间应无共享状态，可并行调查
2. **分层路由**：根据复杂度为每个 scientist 代理分配不同的模型层级
3. **证据驱动**：每个发现必须有代码证据支撑
4. **交叉验证**：所有并行调查结果必须经过交叉验证后才综合
5. **可复现**：另一个代理应能复现每个研究发现

## 执行流程

### 第 1 步：需求分析

- 确认研究目标的范围和边界
- 识别用户的真实研究意图
- 明确成功标准和输出格式

### 第 2 步：维度分解

将研究目标分解为 3-7 个独立研究阶段：

```markdown
## 研究分解

**目标：** <原始研究目标>

### 阶段 1：<阶段名称>
- **焦点：** 该阶段调查什么
- **假设：** 预期发现（如适用）
- **范围：** 需要检查的文件/区域
- **层级：** LOW | MEDIUM | HIGH

### 阶段 2：<阶段名称>
...
```

### 第 3 步：智能模型路由

根据任务复杂度为每个 scientist 分配合适的模型层级：

| 任务复杂度 | 模型层级 | 适用场景 |
|-----------|---------|---------|
| 数据收集（LOW） | haiku | 文件枚举、模式计数、简单查找 |
| 标准分析（MEDIUM） | sonnet | 代码分析、模式检测、文档审查 |
| 复杂推理（HIGH） | opus | 架构分析、跨领域关注点、假设验证 |

### 路由决策指南

| 研究任务 | 层级 | 示例 |
|---------|------|------|
| "统计 X 的出现次数" | LOW | 统计所有 useState 使用次数 |
| "找到所有匹配 Y 的文件" | LOW | 列出项目中所有测试文件 |
| "分析模式 Z" | MEDIUM | 分析 API 路由中的错误处理模式 |
| "记录 W 如何工作" | MEDIUM | 记录认证流程 |
| "解释 X 为什么发生" | HIGH | 解释缓存层中竞态条件的原因 |
| "比较方案 A 与 B" | HIGH | 比较 Redux vs Context 在此的状态管理 |

### 第 4 步：并行分派

一次性分派所有独立阶段的 scientist 代理：

```
// 阶段 1 - 简单数据收集
Task(subagent_type="scientist", model="haiku", prompt="[RESEARCH_STAGE:1] 调查...")

// 阶段 2 - 标准分析
Task(subagent_type="scientist", model="sonnet", prompt="[RESEARCH_STAGE:2] 分析...")

// 阶段 3 - 复杂推理
Task(subagent_type="scientist", model="opus", prompt="[RESEARCH_STAGE:3] 深入分析...")
```

**并发限制**：最多 20 个并行 scientist 代理。超过时分批执行。

### 第 5 步：证据提取

Scientist 使用结构化标签输出发现：

```
[FINDING:<id>] <标题>
<证据和分析>
[/FINDING]

[EVIDENCE:<finding-id>]
- 文件: <路径>
- 行号: <范围>
- 内容: <相关代码/文本>
[/EVIDENCE]

[CONFIDENCE:<level>] # HIGH | MEDIUM | LOW
<置信度理由>
```

**质量门槛**：

| 质量检查 | 要求 |
|---------|------|
| 证据存在 | 每个 [FINDING] 至少 1 个 [EVIDENCE] |
| 置信度声明 | 每个发现都有 [CONFIDENCE] |
| 来源引用 | 文件路径为绝对路径且有效 |
| 可复现 | 另一个代理可以验证 |

### 第 6 步：交叉验证

在所有并行阶段完成后，进行统一交叉验证：

```
// 交叉验证阶段
检查以下内容：
1. 阶段之间的矛盾
2. 缺失的连接
3. 覆盖范围的空白
4. 证据质量

输出：[VERIFIED] 或 [CONFLICTS:<列表>]
```

### 第 7 步：综合报告

生成统一的综合报告：

```markdown
# 研究报告：{目标}

**会话 ID：** {SESSION_ID}
**日期：** {DATE}
**状态：** {STATUS}

## 执行摘要
{2-3 段关键发现总结}

## 方法论
{分解理由和执行策略}

## 关键发现
{每个发现附证据}

## 交叉验证结果
{验证总结，任何已解决的冲突}

## 局限性
{分析盲区和未覆盖区域}

## 建议
{可操作的建议清单}
```

## AUTO 模式

AUTO 模式使研究流程完全自主运行，无需用户中间确认。

- **触发**：`/sciomc AUTO: <研究目标>`
- **最大迭代**：10 轮（可配置）
- **Promise 标签**：
  - `[PROMISE:RESEARCH_COMPLETE]` — 研究成功完成
  - `[PROMISE:RESEARCH_BLOCKED]` — 无法继续
- **状态持久化**：每个阶段完成后持久化进度

## 会话管理

| 命令 | 操作 |
|------|------|
| `sciomc status` | 查看当前会话进度 |
| `sciomc resume` | 恢复最近中断的会话 |
| `sciomc resume <id>` | 恢复指定会话 |
| `sciomc list` | 列出所有会话及状态 |
| `sciomc report <id>` | 生成/重新生成报告 |
| `sciomc cancel` | 取消当前会话（保留状态） |

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 有依赖的阶段并行化 | 红牌。有依赖必须串行 |
| 不交叉验证直接综合 | 红牌。必须先验证再综合 |
| 所有 stage 用同一层级 | 黄牌。应根据复杂度分层路由 |
| 发现无证据支撑 | 红牌。每个发现必须有代码证据 |
| 超过 20 个并行代理 | 黄牌。必须分批执行 |
| 低质量发现不重跑 | 黄牌。质量不达标应重跑该阶段 |
| 覆盖范围遗漏 | 黄牌。交叉验证必须检查覆盖空白 |

## 成功标准

- 所有研究阶段完成或标记失败
- 交叉验证通过（无未解决的冲突）
- 综合报告包含：执行摘要、关键发现、交叉验证结果、局限性和建议
- 每个发现都有代码证据和置信度标注
