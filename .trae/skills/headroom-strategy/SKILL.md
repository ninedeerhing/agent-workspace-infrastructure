# Headroom Strategy — 上下文压缩策略

## 定位

Headroom 是一个上下文优化层技能，位于代理/应用与 LLM 之间。它不是一个"可选优化"，而是处理大规模工具输出时的**默认压缩通道**。每个工具调用输出中 70-95% 是冗余内容——Headroom 在内容到达 LLM 之前压缩，同时保证答案准确率 100%。

## 铁律

> **激进压缩，按需检索。** 压缩不等于丢弃——通过可逆压缩（CCR），LLM 随时可检索完整原始数据。
> **短内容透传。** 小数组（<=10 项）、短文件（<100 行）不做压缩，避免开销大于收益。

## 触发条件

- 工具输出包含 JSON 数组（10+ 项）
- 文件读取内容超过 100 行
- 命令执行输出超过 100 行
- 日志输出或 API 响应内容冗余明显
- 使用 Claude Code / Cursor / Aider 等工具且需要自动压缩
- 需要跨代理会话共享持久记忆
- 前缀缓存命中率低，需要稳定化 prompt 结构

## 六种压缩算法

### SmartCrusher（JSON 压缩器）

**目标**：结构化 JSON 数组的智能压缩。

**策略**：
- 保留前 N 项（schema 推断用）
- 保留后 N 项（最近性）
- 保留所有异常项（errors、warnings、nulls）
- 保留统计分布（数值字段的 min/max/mean）
- 丢弃中间冗余项

**性能参考**：

| 场景 | 原始 Tokens | 压缩后 | 节省 |
|------|------------|--------|------|
| JSON 数组 100 项 | 10.2K | 1.5K | 85.3% |
| JSON 数组 500 项 | 50.2K | 1.5K | 97.0% |
| API 响应 500 项 | 38.9K | 1.1K | 97.2% |

**在小数组中透传**：<=10 项不压缩，直接透传。

### CodeCompressor（AST 感知代码压缩器）

**目标**：源代码的结构化压缩，保留 API 表面。

**策略**：
- 提取函数/类签名（保留 API 表面）
- 压缩函数体（仅保留关键调用和异常路径）
- 删除注释（可配置保留文档注释）
- 删除 import 中未使用的符号

**安全设计**：仅对超长文件（>100 行）激活。短文件透传以保证完整性。

### KompressBase（文本压缩器）

**目标**：自然语言文本和日志的语义压缩。

**策略**：
- 识别并删除冗余段落
- 保留关键信息密度高的句子
- 保留错误代码、数值、日期等结构化信息
- 对技术文档保留操作步骤

**适用内容**：RAG 检索结果、文档页面、日志输出、用户对话历史。

### CacheAligner（前缀缓存稳定化器）

**目标**：稳定化 prompt 前缀，最大化 LLM 提供商 KV Cache 命中率。

**核心规则**：
1. System Prompt 始终排第一（构建最长缓存前缀）
2. 动态内容后移（时间戳、随机 ID 放在末尾）
3. 固定排序（文件列表字典序、JSON key 字母序）

**效果**：在 Anthropic/OpenAI 的 prompt caching 基础上额外提升 20-40% 缓存命中率。

### IntelligentContext（智能上下文填充器）

**目标**：在有限 token 预算内最大化上下文质量。

**策略**：
- 基于重要性评分对内容块排序
- 预算约束下的最佳子集选择（背包问题变体）
- 内容块交叉引用（如果 A 被包含，B 评分自动降低）

**适用场景**：长文档选择、多文件上下文、大量搜索结果筛选。

### CCR（Compress-Cache-Retrieve，可逆压缩）

**目标**：使压缩完全可逆——原始数据永不删除，LLM 按需检索。

**执行流程**：
1. **压缩存储**：原始数据存入缓存
2. **标记注入**：在压缩输出末尾添加原始条目数提示
3. **按需检索**：LLM 发现压缩数据不足时，标注需要完整数据的字段
4. **主动扩展**：后续对话中检测到可能匹配缓存内容时，主动扩展压缩数据

**根本性优势**：消除"激进压缩 vs 信息丢失"的传统权衡——压缩永远可逆。

## 内容路由规则

根据内容类型自动选择压缩器：

| 内容类型 | 判定条件 | 压缩器 | 阈值 |
|----------|----------|--------|------|
| JSON 数组 | 检测到 JSON 数组结构 | SmartCrusher | > 10 项 |
| 源代码 | 识别语言类型 | CodeCompressor | > 100 行 |
| 结构化日志 | 检测到日志模式 | KompressBase | > 100 行 |
| HTML | 检测到 HTML 标签 | 透传或结构提取 | 按需 |
| 短内容 | 以上条件均不满足 | **透传（不压缩）** | N/A |

## 四种集成模式

### Proxy 模式（零代码变更）

```bash
# 启动 Headroom 代理，所有 LLM 请求自动经压缩层
ANTHROPIC_BASE_URL=http://localhost:8787 claude
OPENAI_BASE_URL=http://localhost:8787/v1 your-app
```

**适用**：Claude Code、Cursor、Aider、GitHub Copilot 等现有工具。

### Library 模式（Python SDK）

```python
from headroom import compress

result = compress(messages, model="claude-sonnet-4-5-20250929")
response = client.messages.create(
    model="claude-sonnet-4-5-20250929",
    messages=result.messages,
)
```

**适用**：自定义 Python 应用、LangChain/Agno 集成。

### MCP 模式

```bash
headroom mcp
```

将所有通过 MCP 的工具调用自动压缩。

### Wrap 模式（一键集成）

```bash
headroom wrap claude       # Claude Code
headroom wrap codex        # OpenAI Codex CLI
headroom wrap aider        # Aider
headroom wrap cursor       # Cursor
```

## 跨代理记忆共享

通过 SharedContext 实现跨代理会话的持久记忆：

**支持的记忆源**：
- `CLAUDE.md` / `AGENTS.md` 项目指令文件
- `.reasonix/memory.md` 长期记忆
- 自定义 `.headroom/project-context.md`

**更新策略**：`append`（追加）/ `replace`（替换）/ `merge`（合并）

**故障学习**：当 LLM 因缺少信息而检索完整数据时，记录并自动调整未来压缩策略。

## 与 RTK 策略的协同

| 维度 | Headroom | RTK |
|------|----------|-----|
| 作用层 | 工具输出 → LLM 之间 | 代理内部认知链路 |
| 压缩对象 | 结构化数据（JSON、日志） | 推理链、知识状态、上下文 |
| 触发时机 | 每次工具调用后 | 推理步骤之间 |
| 精度保障 | 保留异常项 + 统计分布 | 保留锚点 + 活跃推理段 |

**推荐组合**：Headroom 处理数据层压缩，RTK 处理认知层压缩。两者叠加可达 **70-85% Token 节省**。当 RTK 的工具输出漏斗激活时，Headroom 的压缩结果直接作为漏斗的第 2 层输入。

## 不需要压缩的场景

| 场景 | 原因 |
|------|------|
| 短对话（<5 轮） | 压缩开销 > 节省 |
| 纯文本聊天 | 输出本身已紧凑 |
| 固定格式 API 调用 | 无重复冗余可压缩 |
| 需要逐字节精度的场景 | 使用透传标记排除 |
| 小数组（<=10 项）、短文件（<100 行） | 压缩无意义 |

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 对小内容压缩 | 红牌。短文件、小数组透传不压缩 |
| 压缩后不保留检索路径 | 红牌。压缩必须可逆（CCR） |
| 压缩错误输出 | 红牌。错误/异常输出始终完整保留 |
| 忽略前缀缓存优化 | 黄牌。动态内容应后移以稳定前缀 |
| 单次工具调用后不做压缩检查 | 黄牌。输出 > 100 行时必须评估压缩 |
| 对 output-heavy 工作流压缩 | 黄牌。Headroom 只压缩输入，不压缩 LLM 输出 |

## 输出物

- 压缩后的工具输出（替代原始输出注入 LLM 上下文）
- 压缩标记（原始条目数、压缩率、使用的压缩器）
- 可逆缓存 key（当使用 CCR 模式时）
- 压缩日志（用于故障学习和策略调整）

## 成功标准

- 大型 JSON/日志输出的 Token 减少 >= 70%
- 关键信息（错误、异常、签名）未被压缩丢失
- 前缀缓存命中率提升（相对于未优化）
- 压缩延迟 < LLM 推理延迟节省（净收益为正）
- 短内容始终透传，零开销
