# Karpathy Guidelines — Karpathy 编码指南

## 定位

来自 Andrej Karpathy 的 LLM 编码行为指南。减少过度复杂化、非手术式修改、隐藏假设和模糊目标的常见错误。

## 触发条件

- 编写任何代码
- 审查代码
- 重构代码
- 实现功能

## 四大核心原则

### 原则 1：编码前思考

- 在写代码之前，先理解问题的全貌
- 阅读相关代码，理解现有模式和约定
- 不要假设——在不确定时先搜索确认
- 思考边界条件和错误状态
- 先有清晰的心智模型再动手

### 原则 2：简洁优先

- 写最少的代码解决问题
- YAGNI：不添加未请求的功能
- 不为了"灵活性"添加未请求的抽象
- 简单的方案优先，只在必要时增加复杂度
- 不要过度工程化

### 原则 3：精准修改（手术式）

- 只改与任务直接相关的文件和代码
- 不做"顺手"重构
- 不添加无请求的新依赖
- 不影响不需要修改的模块
- 每一行变更都能追溯到用户请求

### 原则 4：目标驱动执行

- 明确知道完成的定义
- 先定义验证方法，再开始实现
- 不模糊声称完成——提供证据
- 完成任务后停下来，不做多余的事

## 反模式总结

| 反模式 | 问题 | 纠正 |
|--------|------|------|
| 过度设计 | 添加未请求的抽象层、接口、模式 | YAGNI，只在需要时抽象 |
| 猜测式编码 | 不确认就假设 API、类型、行为 | 先搜索确认，再写代码 |
| 范围蔓延 | 顺手改无关代码 | 严格限定修改范围 |
| 隐藏假设 | 代码依赖未声明的假设 | 明确文档化假设和约束 |
| 模糊完成 | "应该没问题了" | 提供验证证据 |
| 过度注释 | 注释过多或过少 | 代码自解释，注释解释"为什么" |
| 忽略错误处理 | 只处理Happy Path | 考虑所有错误和边界状态 |
| 一次性大提交 | 一次改太多 | 小步提交，每步可验证 |

## 检查清单

编码前：
- [ ] 我理解问题的全貌吗？
- [ ] 我阅读了相关代码吗？
- [ ] 我的修改范围是明确的吗？

编码中：
- [ ] 这是最小的修改吗？
- [ ] 我添加了不必要的抽象吗？
- [ ] 我处理了错误状态吗？

编码后：
- [ ] 我验证了修改吗？
- [ ] 我没有修改无关代码吗？
- [ ] 我能追溯到每个修改的原因吗？
