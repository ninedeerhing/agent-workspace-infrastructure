# Systematic Debugging — 系统化调试

## 铁律

> **NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST**
> 未完成根因调查之前，不得写任何修复代码。

## 定位

调试不是"猜测→修改→重试"的循环，而是严谨的科学方法。本技能强制四阶段流程，确保每次修复都有根因证据支撑。

## 触发条件

- 用户报告 bug 或异常行为
- 测试失败
- 线上错误日志
- 性能退化
- 任何需要调查和修复的场景

## 四阶段流程

### 阶段 1：根因调查（Root Cause Investigation）

**目标**：找到 bug 的真正原因，不是表象。

步骤：
1. **复现**：精确复现 bug，记录最小复现步骤
2. **隔离**：二分法缩小范围——哪次提交、哪个模块、哪个条件
3. **追踪**：从表象往上游追溯数据流/控制流
4. **确认**：找到根因代码行，能解释所有观察到的现象

输出物：
- 最小复现用例
- 根因代码位置（文件:行号）
- 解释链：根因 → 中间影响 → 用户可见症状

**红牌**：以下情况不得进入阶段 2：
- 不能复现
- 不能定位到具体代码行
- 解释链有缺口
- 有替代解释未排除

### 阶段 2：模式分析（Pattern Analysis）

**目标**：确认 bug 是否为系统性问题。

步骤：
1. 搜索同类模式——代码库中是否有相似代码？
2. 判断是单点 bug 还是架构缺陷
3. 如果是架构缺陷，标记为需要设计变更

### 阶段 3：假设与测试（Hypothesize and Test）

**目标**：先提出修复假设，再用测试验证。

步骤：
1. 提出修复方案假设
2. 先写一个复现 bug 的测试（应失败）
3. 应用修复
4. 确认测试通过 + 原复现步骤不再触发
5. 运行回归测试确认无新问题

### 阶段 4：实现（Implementation）

**目标**：在验证后正式提交修复。

步骤：
1. 应用经过验证的修复
2. 如果是系统性问题，修复所有同类实例
3. 运行完整测试套件
4. 记录修复：根因 + 修复 + 验证方法

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 猜测式修复 | 红牌。不允许"试试改这里" |
| 跳过复现 | 红牌。不能复现的 bug 不能声称修复 |
| 修复表象 | 红牌。改日志/吞异常不是修复 |
| 只修一个实例 | 黄牌。系统性 bug 必须修全部实例 |
| 不写回归测试 | 红牌。修复必须包含防止回归的测试 |
| 多问题同时修复 | 黄牌。一次只处理一个根因 |

## 输出物

- 最小复现用例
- 根因分析文档（位置 + 解释链）
- 回归测试
- 修复代码
