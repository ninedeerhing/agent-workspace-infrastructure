# QA Testing — 质量保证测试

## 定位

以 QA Lead 的视角执行系统化测试。四种测试模式覆盖不同场景：Diff-aware、Full、Quick、Regression。

## 触发条件

- 功能实现完成
- 代码审查通过
- 准备验证功能质量

## 四种测试模式

### 模式 1：Diff-Aware（差异感知测试）

**适用**：有明确代码变更范围时。

- 基于 git diff 识别变更范围
- 分析影响的代码路径
- 生成针对性的测试用例
- 覆盖：修改文件 + 依赖方 + 接口边界

### 模式 2：Full（全量测试）

**适用**：重大发布前、架构变更后。

- 运行完整测试套件
- 手动验证关键用户路径
- 跨浏览器/设备测试（如适用）
- 性能基准测试

### 模式 3：Quick（快速冒烟）

**适用**：小修改、热修复。

- 运行核心冒烟测试
- 验证修改的功能
- 检查关键集成点
- 时间：5-10 分钟

### 模式 4：Regression（回归测试）

**适用**：发现回归风险时。

- 运行之前通过的测试
- 对比基准数据
- 检查已知脆弱点
- 确认无性能退化

## 测试维度

每个模式应覆盖：

- [ ] 功能正确性：核心逻辑正确
- [ ] 边界条件：极值、空值、null
- [ ] 错误处理：异常输入、超时、网络失败
- [ ] 状态转换：所有合法/非法状态转换
- [ ] 性能：响应时间、内存使用
- [ ] 安全性：认证、授权、数据保护
- [ ] 兼容性：不同环境、不同数据

## 测试报告模板

```markdown
## QA 测试报告

### 测试模式: [Diff-Aware / Full / Quick / Regression]
### 测试范围: [描述]
### 测试结果: [全部通过 / 部分失败 / 阻塞]
### 发现的问题
1. [严重程度] [描述] [复现步骤]
### 性能指标
- [指标]: [值] vs [基准]
### 建议
- ...
```

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 只用一种模式 | 黄牌。根据场景选择合适模式 |
| 不测试边界条件 | 红牌。边界条件是 bug 高发区 |
| 只测 Happy Path | 红牌。必须包含错误路径 |
| 不写测试报告 | 黄牌。报告是后续审查的输入 |
