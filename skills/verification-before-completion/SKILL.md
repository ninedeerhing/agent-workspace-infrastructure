# Verification Before Completion — 完成前验证

## 铁律

> **NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE**
> 没有新鲜的验证证据，不得声明任务完成。

## 定位

"我觉得应该没问题"不是完成。本技能确保每个完成声明都有新鲜、可重现的验证证据支撑。

## 触发条件

- 准备向用户声明任务完成
- 完成了一组修改
- 准备关闭一个功能分支
- 准备提交 PR
- 准备部署

## 验证优先级

```
针对性测试 → 类型检查/Lint → 构建 → 冒烟测试/E2E → 手动审查
```

按此顺序执行。不能执行某级别验证时，必须说明原因并使用次优证据。

## 验证步骤

### 第 1 步：确认修改范围

- 列出所有被修改的文件
- 确认修改范围与任务目标一致
- 不应有超出范围的修改

### 第 2 步：运行自动化验证

按优先级执行：

1. **针对性测试**：与本次修改直接相关的单元测试/集成测试
2. **类型检查**：`tsc --noEmit` / `mypy` / 项目配置的类型检查命令
3. **Lint 检查**：`eslint` / `ruff` / 项目配置的 lint 命令
4. **完整构建**：`npm run build` / `cargo build` / 项目构建命令
5. **完整测试套件**：所有测试

### 第 3 步：功能验证

- 对照原始需求，逐项确认
- 针对边界条件手工验证（如适用）
- 检查错误状态和空状态

### 第 4 步：记录验证证据

每次验证必须记录：
- 执行的命令
- 命令输出摘要（通过/失败/警告）
- 时间戳
- 如果有失败项，记录具体失败信息和处理决定

### 第 5 步：确认非目标未被影响

- 检查修改是否意外影响了其他功能
- 确认不需要修改的模块未被触及

## 完成声明模板

```
## 完成声明

### 修改文件
- [文件路径] — [修改说明]

### 验证结果
- [验证类型]: 通过/失败 [证据]

### 未验证风险
- [列出因环境限制未能验证的项目及理由]

### 下一步建议
- [如有]
```

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 口头声称完成 | 红牌。必须有验证证据 |
| 用过期的验证结果 | 红牌。每次声明前必须重新验证 |
| 跳过关键验证 | 红牌。不能跳过针对性测试和类型检查 |
| 忽略验证失败 | 红牌。任何失败必须处理或记录决策 |
| 验证范围不完整 | 黄牌。需确认所有受影响模块都验证 |
| 仅依赖手动测试 | 黄牌。优先自动化验证 |

## 不能运行验证时的处理

当环境限制导致无法运行某些验证时：
1. 明确说明哪些验证无法运行及原因
2. 使用次优验证方法（如手动审查、代码走查）
3. 在完成声明中标注为"未验证风险"
4. 建议用户在合适环境中补充验证
