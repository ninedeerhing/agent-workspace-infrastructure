# Test-Driven Development — 测试驱动开发

## 铁律

> **NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST**
> 没有先写失败的测试，就不允许写任何生产代码。

## 定位

TDD 不是测试策略，而是**设计策略**。通过先写测试来驱动接口设计，确保代码可测试、低耦合、高内聚。

## 触发条件

- 准备写任何生产代码（功能实现或 bug 修复）
- 在执行 `writing-plans` 或 `executing-plans` 的每一步时自动触发
- `subagent-driven-dev` 中的每个实现子代理自动遵循

## RED-GREEN-REFACTOR 循环

### 阶段 1：RED（写失败测试）

1. 基于需求写一个最小的、会失败的测试
2. 运行测试，确认测试**确实失败**（不是语法错误或配置问题导致的失败）
3. 确认失败原因正是"功能尚未实现"
4. 如果测试在未实现时通过了，说明测试无效——重写

### 阶段 2：GREEN（最小实现）

1. 写**刚好足够**让测试通过的实现代码
2. 不写任何超出测试覆盖的代码
3. 不优化、不重构、不抽象
4. 运行测试，确认通过

### 阶段 3：REFACTOR（重构）

1. 在测试保护下改善代码结构
2. 消除重复、改善命名、提取方法
3. 每次重构后运行测试确保仍然通过
4. 保持测试速度——慢的测试也是设计问题

## 反模式表

| 反模式 | 说明 | 纠正 |
|--------|------|------|
| 先写实现再补测试 | 红牌。违反铁律 | 回退实现，先写测试 |
| 测试覆盖过多 | 黄牌。一次测太多导致调试困难 | 一个测试只测一个行为 |
| 测试与实现耦合 | 黄牌。测实现细节而非行为 | 测试公共接口，不测私有方法 |
| 跳过 REFACTOR | 黄牌。测试通过就停下 | 必须重构后再进入下一步 |
| 测试未真正失败 | 红牌。测试用错误方式失败 | 确认失败原因正确 |
| Mock 过多 | 黄牌。过度 mock 掩盖集成问题 | 优先用真实对象，只在必要时 mock |
| 测试命名不清晰 | 黄牌。看不懂测试意图 | 用 `should_xxx_when_yyy` 命名模式 |

## 测试结构模板

```
准备（Arrange）→ 执行（Act）→ 断言（Assert）
```

每个测试应清晰对应此三段结构。

## 成功标准

- 每一步实现都有对应的失败测试先于实现
- 测试精确覆盖需求行为
- 重构后测试仍全部通过
- 测试可读性高，可作为文档使用
