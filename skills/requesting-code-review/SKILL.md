# Requesting Code Review — 请求代码审查

## 定位

分派一个通用的、无偏见的子代理来执行代码审查。审查者不参与实现，能从独立视角发现问题和改进机会。

## 触发条件

- 完成了一个任务或功能的实现
- 在 `subagent-driven-dev` 流程中的审查步骤
- 在 `executing-plans` 流程中完成一组步骤后
- 准备提交代码前

## 审查输出结构

审查报告必须包含以下五个部分：

### 1. Strengths（优点）

- 代码中做得好的地方
- 值得保持的模式和做法
- 特别优雅的解决方案

### 2. Issues（问题）

按严重程度分三级：

**Critical（严重）**
- 功能错误或逻辑缺陷
- 安全漏洞
- 数据丢失风险
- 可能导致生产事故的代码
- **必须先修复再继续**

**Important（重要）**
- 性能问题
- 可维护性问题
- 缺少错误处理
- 测试覆盖不足
- **应在合并前修复**

**Minor（轻微）**
- 命名建议
- 代码风格
- 文档注释
- 可读性改进
- **可以后续优化**

### 3. Recommendations（建议）

- 具体的改进建议
- 代码示例（如适用）
- 优先级排序

### 4. Assessment（评估）

- 总体评价：Approve / Approve with Comments / Request Changes
- 是否可以合并
- 需要关注的区域

### 5. Summary（总结）

- 一句话总结审查结论
- 关键数据：文件数、问题数、严重程度分布

## 审查原则

1. **客观**：基于代码质量而非个人偏好
2. **具体**：每个问题都要指向具体代码行
3. **建设性**：指出问题的同时给出改进方案
4. **全面**：覆盖功能、安全、性能、可维护性、测试

## 审查检查清单

- [ ] 功能逻辑是否正确
- [ ] 边界条件和错误状态是否处理
- [ ] 是否有安全漏洞（注入、XSS、敏感数据暴露等）
- [ ] 性能是否有明显瓶颈
- [ ] 代码是否可读、可维护
- [ ] 是否符合项目代码规范
- [ ] 测试覆盖是否充分
- [ ] 是否有不必要的依赖或耦合
- [ ] API 设计是否合理
- [ ] 数据库查询是否高效

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 实施者审查自己的代码 | 红牌。审查必须由独立代理或审查者执行 |
| 只提问题不给方案 | 黄牌。每个问题应附带改进建议 |
| 审查过于笼统 | 黄牌。问题必须指向具体代码位置 |
| 忽略安全审查 | 红牌。安全问题是 Critical 级别的 |
| 审查周期过长 | 黄牌。审查应在 15 分钟内完成 |
