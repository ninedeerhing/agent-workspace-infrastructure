# Writing Plans — 编写实现计划

## 定位

在有了设计规范/需求之后、触碰任何代码之前必须使用。本技能将设计文档转化为可执行的、增量式的实现计划。每个步骤都是可独立验证的小任务。

## 触发条件

- 完成了 brainstorming，设计已确认
- 已有明确的需求文档或规范
- 准备开始编码实现
- 用户说"开始实现"或"写代码"

## 核心原则

1. **2-5 分钟任务粒度**：每个步骤应该可以在 2-5 分钟内完成
2. **TDD 内建**：每步遵循 写测试 → 验证失败 → 写实现 → 验证通过
3. **无占位符**：每步包含完整代码，不写 `// TODO` 或 `...`
4. **文件结构映射**：明确每个步骤涉及的文件和路径

## 计划结构

一个合格的计划必须包含以下结构：

```
计划名称: xxx
目标: 一句话描述最终交付物
非目标: 明确不做的事
前置条件: 依赖的设计文档/环境
步骤列表: 按顺序排列的增量步骤
```

### 每个步骤的格式

```
步骤 N: [步骤名称]
- 涉及文件: [文件路径列表]
- 测试: [测试代码或测试描述]
- 实现: [完整实现代码]
- 验证: [如何确认该步骤完成]
```

## 执行策略

1. **增量式构建**：每个步骤在前一步骤的基础上构建
2. **可回滚**：每个步骤完成后应可独立回滚
3. **持续可运行**：每个步骤完成后代码应可编译/运行
4. **文件优先**：先创建/修改文件结构，再填充逻辑

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 步骤过大 | 红牌。超过 5 分钟工作量的步骤必须拆分 |
| 含占位符 | 红牌。不允许 `// TODO`、`...`、`stub` |
| 跳过测试步骤 | 红牌。每步必须有测试步骤 |
| 未映射文件 | 黄牌。每个步骤必须明确涉及的文件路径 |
| 忽略依赖顺序 | 红牌。步骤必须按依赖关系排序 |
| 无验证标准 | 黄牌。每步必须明确如何验证完成 |

## 输出物

- 完整的实现计划文档
- 每步包含：文件路径、测试、实现代码、验证方法
- 明确的步骤依赖关系
