# Receiving Code Review — 接收代码审查

## 定位

收到代码审查后，不应盲目接受所有建议，也不应防御性拒绝。本技能提供结构化的审查响应流程。

## 触发条件

- 收到了 `requesting-code-review` 或其他代码审查的反馈
- 审查报告中有需要处理的问题

## 6 步响应模式

### 第 1 步：READ（通读）

- 完整阅读审查报告，不做任何判断
- 理解审查者的视角和关注点
- 标记不理解或需要澄清的部分

### 第 2 步：UNDERSTAND（理解）

- 逐条确认理解审查者的问题和建议
- 如有歧义，先与审查者澄清
- 确认每个问题指向的具体代码位置
- 区分事实性错误和建议性改进

### 第 3 步：VERIFY（验证）

- 对每个 Critical 和 Important 级别的问题进行独立验证
- 如果审查者指出的问题确实存在，确认并记录
- 如果审查者的判断有误，准备证据和解释

### 第 4 步：EVALUATE（评估）

对每个问题进行评估和分类：

| 分类 | 处理方式 |
|------|----------|
| 同意，立即修复 | 按建议修改代码 |
| 同意，但方案不同 | 采用替代方案，解释原因 |
| 不同意，有充分理由 | 礼貌说明理由和数据支撑 |
| 需要讨论 | 标记为需要与审查者/团队讨论 |

### 第 5 步：RESPOND（响应）

- 对每个问题给出明确回应
- 格式：`[问题ID] — [决定] — [理由/行动]`
- 对修改的部分提供新的代码或 diff

### 第 6 步：IMPLEMENT（实现）

- 按评估结果逐一修改代码
- 每次修改后运行相关测试
- 修改完成后重新请求审查

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 跳过验证直接修改 | 黄牌。先验证问题确实存在 |
| 争论代码风格 | 黄牌。风格问题用 lint 工具解决 |
| 忽视 Critical 问题 | 红牌。Critical 问题必须修复 |
| 全部接受不思考 | 黄牌。每个建议都应有独立判断 |
| 修改超出审查范围 | 红牌。不要借审查机会做额外重构 |
