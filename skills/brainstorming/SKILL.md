# Brainstorming — 创意头脑风暴

## 定位

**HARD-GATE**：在任何创造性工作之前必须加载本技能。不得跳过。

本技能确保在写任何代码之前，先完成充分的需求探索、方案比较和设计文档输出。它是所有实现工作的第一道关口。

## 触发条件

- 用户要求实现新功能
- 用户要求构建组件、页面、模块
- 用户要求修改现有行为逻辑
- 任何涉及设计决策的创造性工作

## 核心原则

1. **一次一个问题**：每次只聚焦一个设计决策，不要跳跃
2. **YAGNI（You Aren't Gonna Need It）**：不实现当前不需要的东西
3. **为隔离性设计**：每个模块应可独立理解、测试和替换
4. **先发散再收敛**：先穷举方案，再权衡选择
5. **写下来**：所有设计决策必须写入设计文档，不允许仅存在于对话中

## 9 步检查清单

### 第 1 步：探索上下文

- 阅读相关现有代码，理解当前架构和模式
- 识别受影响的模块和文件
- 确认技术栈和约束
- 记录现有接口和数据结构

### 第 2 步：视觉伴侣

- 如果涉及 UI，创建线框图或组件树
- 如果涉及数据流，绘制数据流图
- 如果涉及状态机，绘制状态转换图
- 视觉化有助于发现隐藏假设

### 第 3 步：逐一澄清

- 逐个提出歧义点，等待用户澄清
- 不要批量提问——一次一个，确保每个都理解到位
- 用自己的话复述用户意图，确认理解一致
- 记录所有澄清结果

### 第 4 步：生成 2-3 方案 + 权衡

- 为每个关键设计决策生成至少 2 个可行方案
- 每个方案列出：优点、缺点、适用场景、风险
- 给出推荐方案和理由
- 不要过早锁定单一方案

### 第 5 步：分节设计

- 将设计按关注点分节（数据模型、API、UI、状态管理、错误处理等）
- 每节独立可审查
- 确保节之间接口清晰

### 第 6 步：写入设计文档

- 将完整设计写入文件（如 `docs/design-xxx.md` 或项目约定的位置）
- 包含：目标、非目标、方案对比、推荐方案、实现步骤、风险
- 这是后续 `writing-plans` 技能的输入

### 第 7 步：规范自审

- 对照以下检查清单自审设计：
  - [ ] 所有用户交互路径是否覆盖？
  - [ ] 错误状态是否处理？
  - [ ] 加载状态是否处理？
  - [ ] 空状态是否处理？
  - [ ] 边界条件是否考虑？
  - [ ] 安全性是否有隐患？
  - [ ] 性能是否有瓶颈？
  - [ ] 是否过度设计？

### 第 8 步：用户审查

- 将设计文档呈现给用户
- 明确标注关键决策点和替代方案
- 等待用户确认或修改

### 第 9 步：过渡到 writing-plans

- 设计确认后，立即建议加载 `writing-plans` 技能
- 将设计文档作为 `writing-plans` 的输入

## 反模式 / 红牌

| 反模式 | 说明 |
|--------|------|
| 跳过设计直接写代码 | 红牌。必须先完成设计文档 |
| 方案只有一个 | 黄牌。至少 2 个方案，否则没有真正思考 |
| 批量提问 | 黄牌。一次一个澄清问题 |
| 设计留在对话中 | 红牌。必须写入持久化文档 |
| 过度设计 | 黄牌。YAGNI——不要为假设的未来需求设计 |
| 忽略现有代码 | 红牌。必须先理解当前代码库 |

## 输出物

1. **设计文档**：持久化的设计文档文件
2. **方案对比表**：至少 2 个方案的优缺点分析
3. **澄清记录**：所有歧义点的澄清结论
4. **过渡信号**：明确告知用户进入下一阶段（writing-plans）

## 成功标准

- 用户确认设计方案
- 设计文档已写入文件
- 所有歧义点已澄清
- 方案选择有明确理由
- 非目标已明确标注
